# ADR-0010: Adopt the RQML 2.2.0 compact trace-edge form

- **Status**: Accepted
- **Date**: 2026-07-23
- **Classification**: `required_by_spec`
- **Supersedes**: `ADR-0003` (migrate trace links to the canonical nested `<edge>` form)
- **Related requirements**: `REQ-UI-006J`, `REQ-UI-013`
- **Affected components**: `requirements.rqml`, `syntaxes/rqml.tmLanguage.json`, `src/transformers/`, `package.json`

## Context

`ADR-0003` moved this project from the flat `2.0.1` `<traceEdge>` attribute form
to the nested `2.1.0` form, in which each endpoint is a `<locator>` element
wrapping a `<local>`, `<doc>` or `<external>` child. That was correct for
`2.1.0` and remains the right account of why the flat form was abandoned.

RQML `2.2.0` replaces the nested form with a compact one. An edge carries its
endpoints as required `from` and `to` attributes using a lexically
discriminated micro-syntax: a bare id is local, an `rqml:<doc-uri>#<id>` value
with optional pins is a document reference, and any other scheme URI or
relative path is external. The `@kind` and `@title` hints that lived on the
locator become per-side `fromKind`/`toKind` and `fromTitle`/`toTitle`
attributes. The three locator kinds are unchanged in meaning; only the
serialization changed.

So `ADR-0003`'s decision — "use the canonical nested `<edge>` form
exclusively" — now names a form the current schema does not accept. It cannot
stand as the project's guidance, and it is immutable, so it needs superseding
rather than editing.

## Decision drivers

- The project targets one schema version at a time and dogfoods it; its own
  specification must be on the version the extension tells users to write.
- The extension had fallen behind the engine badly enough that it could not
  open a document produced by a current `rqml init`. Staying on `2.1.0` would
  have preserved that gap.
- The compact form is materially smaller, and trace sections are the bulk of a
  mature specification.

## Options considered

1. **Stay on `2.1.0`.** Keeps `ADR-0003` accurate and avoids a large diff, but
   leaves the project on a superseded serialization while shipping a tool whose
   purpose is to keep people current. Rejected.
2. **Support both forms as first-class and write whichever the document
   already uses.** The engine reads both regardless, so this costs nothing at
   read time — but it means two shapes in the project's own document over time
   and no single answer to "what do we write". Rejected.
3. **Adopt `2.2.0` as the version this project writes, while continuing to read
   `2.0.1` and `2.1.0`.** Chosen.

## Decision

This project's specification is `2.2.0`, and its trace section uses the compact
`<edge id= type= from= to=>` form. The migration was mechanical, via
`rqml migrate`: 154 edges rewritten, 206,556 → 192,993 bytes.

New specifications created by the extension are `2.2.0`. Documents at `2.0.1`
and `2.1.0` remain readable, and the schema catalogue that decides this is
`@rqml/schema`'s rather than a list the extension maintains (`ADR-0008`).

Equivalence was verified rather than assumed: parsing both revisions with
`@rqml/core` `0.8.0` yields 154 edges with identical `{id, type, from, to}`
tuples. Both serializations normalise to the same typed model, which is why the
matrix, trace graph and export transformers needed no change — they consume the
typed `Locator`, not the XML shape.

The TextMate grammar was corrected in the same change. It matched `traceEdge`,
the `2.0.1` name retired by `ADR-0003`, and never matched `edge` — so trace
edges had gone unhighlighted since that migration. It now covers the compact
form and its endpoint attributes, and retains the nested elements so `2.0.1`
and `2.1.0` documents still read well.

## Consequences

**Positive**
- The project writes the version it tells users to write.
- A 6.6% smaller specification, concentrated in the section that grows fastest.
- Endpoints are legible in the source without following two levels of nesting.

**Negative**
- Any tool consuming this repository's specification directly, rather than
  through `@rqml/core`, must understand the micro-syntax. Nothing does today,
  but a naive XPath over `edge/from/locator/local/@id` would now find nothing.
- The migration touched every trace edge, so `git blame` on that section points
  at the migration commit rather than at the change that introduced each edge.
- Reading three serializations is a permanent obligation for as long as
  documents in the wild use the older two.

## Supersession

None. This ADR is current, and supersedes `ADR-0003`.
